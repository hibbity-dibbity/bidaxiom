# Component Organization

This document defines component extraction and organization conventions for the Next.js web app.

## Directory Structure

```
components/
├── ui/                    # Base design system (shadcn/ui)
│   ├── button.tsx
│   ├── form.tsx
│   └── ...
├── shared/                # Extracted domain-agnostic (3+ uses)
│   ├── status-badge.tsx
│   ├── currency-display.tsx
│   └── ...
├── [domain]/              # Domain-specific components
│   ├── project/
│   ├── budget/
│   ├── estimates/
│   └── ...
└── layout/                # App-wide layout
    ├── sidebar.tsx
    ├── topbar.tsx
    └── ...
```

## Extraction Threshold: 3+ Uses

Components should be extracted to `shared/` only when:
1. Used in 3+ locations across different domains
2. Unlikely to diverge per use case
3. Complex enough to warrant extraction

### Decision Tree

1. **Is it used 3+ times?**
   - No → Keep in domain folder
   - Yes → Continue to #2

2. **Is it domain-specific?**
   - Yes → Keep in `components/[domain]/`
   - No → Continue to #3

3. **Will it diverge per use?**
   - Yes → Don't extract (accept duplication)
   - No → Continue to #4

4. **Is it complex enough to warrant extraction?**
   - No → Keep inline
   - Yes → Extract to `shared/`

### Examples

**Extract to shared/:**
- StatusBadge (used across RFQs, estimates, integrations - 6+ uses)
- CurrencyDisplay (used across budgets, estimates, projects - 14+ uses)
- DataTable (if used for projects, bids, estimates - 3+ uses)

**Keep in domain:**
- EstimateLineItemsTable (only used in estimates workflow)
- BudgetVarianceChart (only used in budget views)
- RFQForm (only used in bidding)

**Don't extract (accept duplication):**
- Form layouts that will diverge per feature
- One-off page components
- Components with high coupling to specific domain logic

## Naming Conventions

- **File names:** kebab-case (e.g., `status-badge.tsx`)
- **Component exports:** PascalCase (e.g., `StatusBadge`)
- **Utility exports:** camelCase (e.g., `formatCurrency`)

## CVA Variants

Use class-variance-authority for component variants:

```typescript
const componentVariants = cva(
  "base-classes",
  {
    variants: {
      variant: { ... },
      size: { ... },
    },
    defaultVariants: { ... },
  }
);
```

**Limits:**
- 3-5 variant dimensions per component
- Prioritize design system consistency over flexibility
- Don't encode business logic in variants

## Import Patterns

**DO:**
```typescript
import { StatusBadge } from "@/components/shared/status-badge";
import { Button } from "@/components/ui/button";
```

**DON'T:**
```typescript
import { StatusBadge } from "@/components/shared"; // Barrel export
```

Barrel exports break tree-shaking and inflate bundles.

## Component APIs

- Keep props focused (3-5 props ideal)
- Use composition over configuration
- Prefer controlled components for shared UI
- Document non-obvious props with JSDoc

## References

- Research: `.planning/phases/19-component-library-architecture/19-RESEARCH.md`
- Context: `.planning/phases/19-component-library-architecture/19-CONTEXT.md`

# Routing Conventions

This document defines URL structure, routing patterns, and navigation conventions for the Next.js web app.

## URL Hygiene Standards

All user-facing entity URLs use slug-based routing:

| Entity | URL Pattern | Example |
|--------|-------------|---------|
| Project | `/projects/[jobNumber]-[name]` | `/projects/24001-main-street-renovation` |
| Customer | `/customers/cust-[id]-[name]` | `/customers/cust-12345678-abc-construction` |
| Subcontractor | `/subcontractors/sub-[id]-[name]` | `/subcontractors/sub-87654321-acme-hvac` |
| Estimate | `/estimates/est-[jobNumber]-[name]` | `/estimates/est-24001-main-street-estimate` |

### Benefits

- **Bookmarkable:** Users can save and share meaningful links
- **SEO-friendly:** Descriptive URLs improve search rankings
- **Self-documenting:** Job number + name visible in URL
- **User-readable:** No UUIDs in user-facing URLs

## Slug Generation

Centralized in `apps/api/src/utils/slug.ts`:

```typescript
import { generateSlug } from "@/utils/slug";

const slug = generateSlug(identifier, name);
// "24001", "Main Street Renovation" → "24001-main-street-renovation"
```

**Rules:**
- Lowercase only
- Hyphens for spaces
- No special characters
- Unique per tenant schema

## Dynamic Route Patterns

### Persistent Headers with Layout

For entity detail pages with persistent headers (project, customer, etc.):

```
[entitySlug]/
  ├── layout.tsx      # Persistent header + tabs
  ├── page.tsx        # Default tab (overview)
  ├── budget/
  │   └── page.tsx    # Budget tab
  └── documents/
      └── page.tsx    # Documents tab
```

**Layout.tsx:**
```typescript
export default function EntityLayout({ children, params }) {
  const { data: entity } = trpc.entity.getBySlug.useQuery({
    slug: params.entitySlug,
  });

  return (
    <div>
      <EntityHeader entity={entity} />  {/* Never reloads */}
      <EntityTabs entitySlug={params.entitySlug} />  {/* Never reloads */}
      <div>{children}</div>  {/* page.tsx renders here */}
    </div>
  );
}
```

## Prefetching Strategy

### Hover Prefetch (Recommended)

Prefetch data when user hovers over link:

```typescript
const utils = trpc.useUtils();

const prefetchBudget = () => {
  utils.budget.getProjectSummary.prefetch({ projectId });
};

<Link
  href="/projects/24001-renovation/budget"
  scroll={false}
  onMouseEnter={prefetchBudget}
>
  Budget
</Link>
```

**Benefits:**
- Only prefetches likely navigation
- Navigation feels instant when user clicks
- Reduces unnecessary data fetching

### Viewport Prefetch (Avoid)

Do NOT rely on viewport prefetch alone - it prefetches all visible links:
- Wastes bandwidth
- Increases server load
- Prefetches unlikely navigation

## Scroll Restoration

### List Pages

Remember scroll position when navigating back:

```typescript
useEffect(() => {
  const savedScroll = sessionStorage.getItem('projectListScroll');
  if (savedScroll) {
    window.scrollTo(0, parseInt(savedScroll));
  }
}, []);
```

### Detail Pages

Reset scroll to top when navigating to detail:

```typescript
<Link href={`/projects/${project.slug}`} scroll={true}>
  {project.name}
</Link>
```

### Tab Navigation

Maintain scroll when switching tabs:

```typescript
<Link href={`/projects/${slug}/budget`} scroll={false}>
  Budget
</Link>
```

## Migration from UUID Routes

When migrating from UUID to slug routes:

1. Add slug column with migration script
2. Create slug-based routes ([entitySlug])
3. Add redirect from old UUID route:

```typescript
// Old route: [entityId]/page.tsx
export default function EntityRedirect({ params }) {
  const { data: entity } = trpc.entity.getById.useQuery({ id: params.entityId });

  if (entity?.slug) {
    redirect(`/entity/${entity.slug}`);
  }
}
```

4. Update all internal links to use slugs
5. Remove old routes after transition period

## References

- Slug utilities: `apps/api/src/utils/slug.ts`
- Research: `.planning/phases/19-component-library-architecture/19-RESEARCH.md`
```

# Validation Schema Conventions

This document defines Zod schema patterns for client-server validation sharing.

## Single Source of Truth

All validation schemas live in `packages/shared/src/schemas/` and are imported by both:
- **Client:** React Hook Form via zodResolver
- **Server:** tRPC procedures via .input()

This prevents validation drift where client passes but server rejects.

## Schema Organization

```
packages/shared/src/schemas/
├── common.ts          # Shared primitives (phone, address, date)
├── project.ts         # Project schemas
├── customer.ts        # Customer schemas
├── budget.ts          # Budget schemas
├── estimates.ts       # Estimate schemas
└── index.ts           # Central export
```

## Schema Patterns

### Create Schema

Used by client forms and server create mutations:

```typescript
export const createEntitySchema = z.object({
  name: z.string().min(1, "Name is required").max(200),
  email: z.string().email("Invalid email"),
  phone: phoneSchema,          // Reuse from common.ts
  address: addressSchema,      // Reuse from common.ts
  // All required fields for creation
});

export type CreateEntityInput = z.infer<typeof createEntitySchema>;
```

### Update Schema

Used by client edit forms and server update mutations:

```typescript
export const updateEntitySchema = createEntitySchema.partial();

export type UpdateEntityInput = z.infer<typeof updateEntitySchema>;
```

**Pattern:** `.partial()` makes all fields optional for updates.

### Filter Schema

Used by list pages with nuqs and server list queries:

```typescript
export const entityFilterSchema = z.object({
  search: z.string().optional(),
  status: z.enum(["active", "inactive"]).optional(),
  page: z.coerce.number().min(1).default(1),
  limit: z.coerce.number().min(1).max(100).default(20),
});

export type EntityFilter = z.infer<typeof entityFilterSchema>;
```

**Pattern:** All fields optional for flexible filtering, coerce for URL params.

## Validation Messages

Include user-friendly messages in schema (not component):

```typescript
// GOOD
name: z.string().min(1, "Name is required").max(200, "Name too long")

// BAD (error message in component)
name: z.string().min(1)
// Component: {errors.name && <span>Name is required</span>}
```

**Why:** Centralized messages prevent inconsistency.

## Async Validation

For uniqueness checks or external validation:

```typescript
email: z.string().email().refine(
  async (email) => {
    const exists = await checkEmailExists(email);
    return !exists;
  },
  { message: "Email already registered" }
)
```

**Important:** Use `mode: "onBlur"` in useForm for async validation:

```typescript
const form = useForm({
  mode: "onBlur",  // Not onChange
  resolver: zodResolver(schema),
});
```

## Reusing Common Schemas

Import from common.ts instead of duplicating:

```typescript
import { phoneSchema, addressSchema } from "./common";

export const customerSchema = z.object({
  name: z.string().min(1),
  phone: phoneSchema,        // Don't redefine
  address: addressSchema,    // Don't redefine
});
```

## Client Usage

```typescript
import { createProjectSchema, type CreateProjectInput } from "@construction/shared";
import { zodResolver } from "@hookform/resolvers/zod";

export function ProjectForm() {
  const form = useForm<CreateProjectInput>({
    resolver: zodResolver(createProjectSchema),
  });

  // Form fields inferred from schema
}
```

## Server Usage

```typescript
import { createProjectSchema, updateProjectSchema } from "@construction/shared";

export const projectRouter = router({
  create: protectedProcedure
    .input(createProjectSchema)
    .mutation(async ({ ctx, input }) => {
      // input is CreateProjectInput type
    }),

  update: protectedProcedure
    .input(z.object({
      id: z.string().uuid(),
      data: updateProjectSchema,
    }))
    .mutation(async ({ ctx, input }) => {
      // ...
    }),
});
```

## Migration from Local Schemas

When consolidating local schemas:

1. Create schema in `packages/shared/src/schemas/[entity].ts`
2. Export from `index.ts`
3. Update client: replace local schema with import
4. Update server: replace .input(z.object({...})) with .input(schema)
5. Remove local schema definition
6. Verify TypeScript compilation

## Anti-Patterns

**DON'T duplicate schemas:**
```typescript
// Client
const formSchema = z.object({ name: z.string().min(1) });

// Server
.input(z.object({ name: z.string().min(1) }))  // DUPLICATION
```

**DO import shared schema:**
```typescript
import { createEntitySchema } from "@construction/shared";

// Client
const form = useForm({ resolver: zodResolver(createEntitySchema) });

// Server
.input(createEntitySchema)
```

## References

- Common schemas: `packages/shared/src/schemas/common.ts`
- Research: `.planning/phases/19-component-library-architecture/19-RESEARCH.md`
