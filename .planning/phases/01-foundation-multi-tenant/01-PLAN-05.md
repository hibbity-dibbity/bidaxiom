Implement policy-based access control (PBAC) using CASL. Define role-based abilities (admin, project_manager, member, etc.), create tRPC middleware to inject abilities into context, and set up client-side conditional rendering.

Output: CASL ability definitions, tRPC authorization middleware, client-side ability hooks.

      - can('manage', 'Project')
      - can('manage', 'Budget')
      - can('manage', 'ChangeOrder')
      - can('manage', 'PayApplication')
      - can('read', 'Bid')
      - can('read', 'RFQ')
      - can('read', 'AuditLog')

      - can('read', 'Project')
      - can('update', 'Project', { assignedTo: userId }) — only assigned projects
      - can('read', 'Budget')
      - can('read', 'ChangeOrder')
      - cannot('manage', 'CompanySettings')
      - cannot('delete', 'all')

      org:estimator:
      - can('manage', 'Bid')
      - can('manage', 'RFQ')
      - can('read', 'Project')
      - can('read', 'Budget')
      - cannot('manage', 'CompanySettings')

      - can('read', 'ChangeOrder')
      - can('read', 'Project')
      - can('read', 'AuditLog')
      - cannot('manage', 'CompanySettings')

  <action>
    apps/api/src/trpc/middleware/authorize.ts:
    - Export middleware function withAbilities that:
      1. Gets ctx.orgRole and ctx.userId from tRPC context
      2. Calls defineAbilitiesFor(ctx.orgRole, ctx.userId)
      3. Injects abilities into ctx via next({ ctx: { ...ctx, abilities } })
    - Export helper function requirePermission(action, subject) that returns a middleware:
      1. Gets ctx.abilities
      2. Calls ForbiddenError.from(abilities).throwUnlessCan(action, subject)
      3. Maps CASL ForbiddenError to TRPCError with code 'FORBIDDEN'

    apps/api/src/trpc/procedures.ts — Update:
    - Add authorizedProcedure: protectedProcedure extended with withAbilities middleware
    - This is the procedure most routes will use going forward
    - Keep protectedProcedure for cases where abilities aren't needed (tenant operations)
    - Procedure hierarchy: publicProcedure -> authProcedure -> protectedProcedure -> authorizedProcedure

    apps/api/src/trpc/routers/tenant.ts — Update:
    - Add tenant.role: protectedProcedure that returns { role: ctx.orgRole, abilities: serialized abilities }
    - This endpoint provides role info to the frontend for CASL client setup

    Install CASL in apps/web: npm install @casl/ability @casl/react

    apps/web/lib/abilities.ts:
    - Import defineAbilitiesFor from shared or duplicate the ability definitions
    - NOTE: CASL is isomorphic — same defineAbilitiesFor works client-side
    - Create React context for abilities:
      - AbilityContext using createContext
      - AbilityProvider component that:
        1. Calls trpc.tenant.role.useQuery() to get user's role
        2. Creates abilities via defineAbilitiesFor(role, userId)
        3. Provides abilities via context
      - useAbilities() hook that returns abilities from context
    - Create Can component using createContextualCan(AbilityContext)
    - Export Can component for declarative permission checks in JSX:
      <Can I="create" a="Project">...</Can>
    - Export useAbilities hook for imperative checks:
      const abilities = useAbilities(); if (abilities.can('delete', 'Project')) { ... }
  </action>

    4. tenant.role endpoint returns correct role and abilities
    5. Client-side: <Can I="manage" a="all"> renders for admin, hidden for member
    6. useAbilities() hook returns correct abilities based on authenticated user's role
  </verify>
