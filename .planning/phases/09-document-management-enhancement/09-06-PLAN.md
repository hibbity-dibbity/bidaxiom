Create new file apps/api/src/trpc/routers/workflow.ts following Phase 5 change order router patterns.

Import schemas from @construction/shared: createWorkflowSchema, submitWorkflowSchema, reviewApprovalSchema, respondToWorkflowSchema, updateWorkflowSchema

Create workflowRouter with 8 procedures:

**1. create** (mutation, protectedProcedure):
- Input: createWorkflowSchema
- Verify document exists and user has "update" permission on Document
- Get document's projectId
- Use transaction with SELECT FOR UPDATE on workflow_counters:
  - Lock counter row for (projectId, workflowType)
  - Increment currentNumber
  - Generate workflowNumber: `${workflowType.toUpperCase()}-${currentNumber.toString().padStart(3, '0')}`
- Insert document_workflows record (status: "draft", createdBy: userId)
- Insert workflow_approvals records from input.approvalSteps
- Insert workflow_history: fromStatus null, toStatus "draft", comment "Workflow created"
- Create audit log: AuditAction.CREATE, entityType: "DocumentWorkflow"
- Return workflow with id and workflowNumber

**2. submit** (mutation, protectedProcedure):
- Input: submitWorkflowSchema
- Verify workflow exists and user is creator OR has "update" permission on Workflow
- Check status is "draft" (can only submit from draft)
- Use transaction:
  - Update workflow: status = "submitted", submittedBy = userId, submittedAt = now()
  - Insert workflow_history: fromStatus "draft", toStatus "submitted"
- Create audit log: AuditAction.UPDATE, entityType: "DocumentWorkflow", changes: { status: { from: "draft", to: "submitted" } }
- Return updated workflow

**3. reviewApproval** (mutation, protectedProcedure):
- Input: reviewApprovalSchema
- Verify approval step exists and workflow is "submitted" or "under_review"
- Check user can approve this step:
  - If requirementType = "specific_user", userId must match approverUserId
  - If requirementType = "any_with_role" or "all_with_role", user must have approverRole in project team
- Use transaction:
  - Update workflow_approvals: status = input.action (approved/rejected), reviewedBy = userId, reviewedAt = now(), comments = input.comments
  - If action = "rejected", update workflow status to "rejected"
  - If action = "approved" and this is last pending step, update workflow status to "approved"
  - Otherwise if first approval, update workflow status to "under_review"
  - Insert workflow_history for approval action
- Create audit log: AuditAction.UPDATE, entityType: "DocumentWorkflow"
- Return updated workflow with approval steps

**4. respond** (mutation, protectedProcedure):
- Input: respondToWorkflowSchema
- Verify workflow exists and user has "update" permission
- Verify response document exists and belongs to same project
- Use transaction:
  - Update workflow: responseDocumentId, respondedBy = userId, respondedAt = now(), status = "closed" if approved
  - Insert workflow_history: comment from input
- Create audit log: AuditAction.UPDATE, entityType: "DocumentWorkflow", changes: { responseDocumentId }
- Return updated workflow

**5. list** (query, protectedProcedure):
- Input: { projectId: UUID, workflowType: optional, status: optional, limit: optional (default 50) }
- Load abilities and check "read" permission on Workflow
- Query document_workflows with filters
- Join to documents, users (for submittedBy, respondedBy)
- Include approval steps status summary (pending count, approved count, rejected count)
- Order by createdAt DESC
- Return array of workflows with metadata

**6. getById** (query, protectedProcedure):
- Input: { workflowId: UUID }
- Verify workflow exists and user has "read" permission
- Query workflow with joins: document, project, approval steps (with reviewers), response document
- Include computed field: canCurrentUserApprove (check if user can approve any pending step)
- Return detailed workflow object

**7. getHistory** (query, protectedProcedure):
- Input: { workflowId: UUID }
- Verify workflow exists and user has "read" permission
- Query workflow_history where workflowId, order by changedAt DESC
- Join to users to get changedBy user name
- Return array of history entries

**8. update** (mutation, protectedProcedure):
- Input: updateWorkflowSchema
- Verify workflow exists and user has "update" permission
- Check status is "draft" (only drafts can be edited)
- Track changed fields for history
- Use transaction: update workflow, insert workflow_history for each changed field
- Create audit log: AuditAction.UPDATE, entityType: "DocumentWorkflow", changes: { field: { from, to } }
- Return updated workflow

Follow Phase 5 patterns: SELECT FOR UPDATE for counters, transaction for multi-table updates, status transition validation, audit logging.

In apps/api/src/trpc/router.ts:

- Register in appRouter: `workflow: workflowRouter`

Add Workflow subject permissions to defineAbilitiesFor function following existing Document and ChangeOrder patterns:

**Admin (org:admin):**
- can("manage", "Workflow") - full access to all workflows in tenant

**Project Manager:**
- can("manage", "Workflow", { projectId: { $in: userProjectIds } }) - full access to workflows in their projects

**Superintendent:**
- can("create", "Workflow", { projectId: { $in: userProjectIds } })
- can("read", "Workflow", { projectId: { $in: userProjectIds } })
- can("update", "Workflow", { projectId: { $in: userProjectIds } })
- can("delete", "Workflow", { projectId: { $in: userProjectIds }, status: "draft" }) - only delete drafts

**Estimator:**
- can("create", "Workflow", { projectId: { $in: userProjectIds } })
- can("read", "Workflow", { projectId: { $in: userProjectIds } })
- can("update", "Workflow", { projectId: { $in: userProjectIds } })

**Foreman:**
- can("read", "Workflow", { projectId: { $in: userProjectIds } }) - visibility for awareness
- can("update", "Workflow", { projectId: { $in: userProjectIds }, submittedBy: userId }) - can respond to workflows they created

**Accountant:**
- can("read", "Workflow", { projectId: { $in: userProjectIds } })

**Viewer:**
- can("read", "Workflow", { projectId: { $in: userProjectIds } })

Use $in operator with userProjectIds (from projectTeamMemberships) for project-level scoping, same as Document permissions.

Approval-specific logic (who can approve which steps) is handled in reviewApproval procedure, not CASL - too granular for subject-level rules.
