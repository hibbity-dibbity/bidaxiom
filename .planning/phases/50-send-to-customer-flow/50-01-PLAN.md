  <action>
Add a new `sendToCustomer` mutation procedure to the estimates router, after the existing `submitEstimate` procedure.

The mutation:
- Input: `z.object({ estimateId: z.string().uuid() })`
- Auth guard: `ctx.tenant` + `ctx.userId` must exist (throw INTERNAL_SERVER_ERROR if missing)
- CASL guard: `ForbiddenError.from(abilities).throwUnlessCan("manage", "Estimate")` using `loadProjectAbilities` (same pattern as `submitEstimate`)
- Fetch: select from `schema.estimates` where `id = input.estimateId`, limit 1; throw NOT_FOUND if missing
- Status guard: if `estimate.status === "under_contract"` throw BAD_REQUEST with message "Cannot re-send a proposal that is already under contract"
- Update: set `{ status: "submitted", submittedAt: new Date(), updatedAt: new Date() }` — unconditional (idempotent for all non-under_contract statuses)
- Return: the updated estimate record

This is intentionally idempotent — calling it on a `submitted` or `accepted` estimate just resets to `submitted`. The `under_contract` guard prevents reverting a finalized contract.

Do NOT modify the existing `submitEstimate` procedure. Do NOT modify `canTransitionEstimate` in the lifecycle service.

Pattern reference (from RESEARCH.md Pattern 3): use the exact Drizzle `db.update().set().where().returning()` pattern already used in `submitEstimate`.

- Return: the updated change order record

This bypasses the `VALID_CO_STATUS_TRANSITIONS` state machine intentionally — the business intent is "re-sendable at any time" per CONTEXT.md locked decision. The `submit` procedure (state-machine-aware) remains untouched.
