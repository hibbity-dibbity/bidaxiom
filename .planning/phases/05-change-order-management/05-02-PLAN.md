**Create `apps/api/src/utils/sequential-number.ts`:**

Implement scoped sequential numbering with SELECT FOR UPDATE to prevent race conditions. This utility generates numbers like "PCO-2024-001" and "CO-2024-015" scoped per project per year.

```typescript
import { eq, and, sql } from "drizzle-orm";
import type { NodePgDatabase } from "drizzle-orm/node-postgres";

export async function getNextChangeOrderNumber(
  db: NodePgDatabase<any>,
  changeOrderCounters: any, // tenant schema table
  projectId: string,
  type: "pco" | "co",
  year?: number
): Promise<string> {
  const targetYear = year ?? new Date().getFullYear();

  return await db.transaction(async (tx) => {
    // Use raw SQL for SELECT FOR UPDATE since Drizzle's .for() may not be available
    const counterResult = await tx.execute(
      sql`SELECT id, last_number FROM ${changeOrderCounters}
          WHERE project_id = ${projectId}
          AND type = ${type}
          AND year = ${targetYear}
          FOR UPDATE`
    );

    let nextNumber: number;
    const rows = counterResult.rows as any[];

    if (!rows || rows.length === 0) {
      // First CO/PCO for this project/year — insert counter
      await tx.insert(changeOrderCounters).values({
        projectId,
        type,
        year: targetYear,
        lastNumber: 1,
      });
      nextNumber = 1;
    } else {
      nextNumber = rows[0].last_number + 1;
      await tx
        .update(changeOrderCounters)
        .set({ lastNumber: nextNumber })
        .where(eq(changeOrderCounters.id, rows[0].id));
    }

    const prefix = type === "pco" ? "PCO" : "CO";
    return `${prefix}-${targetYear}-${String(nextNumber).padStart(3, "0")}`;
  });
}
```

**Procedures to implement in this task (CRUD + submit):**

1. **create** (mutation):
   - Input: `createChangeOrderSchema` (discriminated union)
   - Validate project exists and user has manage permission for ChangeOrder
   - For subcontractor type: validate commitmentId exists and belongs to project
   - For each lineItem with budgetLineItemId: validate budget line item exists and belongs to project
   - Create changeOrder record (status: 'draft', totalAmount calculated from sum of lineItems amountChange)
   - Create changeOrderLineItems in same transaction
   - Record history entry: changeType='status_change', oldValue=null, newValue={status:'draft'}
   - Return created change order with line items

2. **list** (query):
   - Input: { projectId, status?, type? }
   - Filter by project, optional status and type filters
   - Return change orders ordered by createdAt DESC
   - Include lineItem count and totalAmount per CO

3. **getById** (query):
   - Input: { id }
   - Return change order with all line items (LEFT JOIN budget line items for context)
   - Include approval steps and history
   - Validate project membership via CASL

4. **update** (mutation):
   - Input: `updateChangeOrderSchema`
   - Only allow updates when status is 'draft' or 'rejected' (throw BAD_REQUEST otherwise)
   - Track field-level changes: for each changed field, insert a changeOrderHistory record with oldValue/newValue
   - Increment revision number (query max revision from history + 1)
   - Update changeOrder record
   - Return updated change order

5. **updateLineItems** (mutation):
   - Input: { changeOrderId, lineItems: array of {budgetLineItemId?, costCodeId, description, amountChange} }
   - Only allow when status is 'draft' or 'rejected'
   - Delete existing line items and insert new ones (replace strategy)
   - Update totalAmount on changeOrder
   - Record history: changeType='line_item_change'
   - Return updated change order with line items

6. **submit** (mutation):
   - Input: `submitForApprovalSchema`
   - Validate status is 'draft' or 'rejected' (resubmission after rejection)
   - Generate PCO number via `getNextChangeOrderNumber(db, schema.changeOrderCounters, projectId, 'pco')`
   - Create approval_workflow_steps records from input.approvalSteps
   - Update status to 'pco_submitted', set submittedAt and submittedBy
   - Record history: changeType='status_change', oldValue={status:'draft'}, newValue={status:'pco_submitted'}
   - Return updated change order with PCO number

7. **delete** (mutation):
   - Input: { id }
   - Only allow when status is 'draft' (throw FORBIDDEN otherwise)
   - Delete change order (cascades to line items, steps, history)
   - Return { success: true }

Add 4 more procedures to the change-order.ts router created in Task 1:

**8. approve** (mutation):
   - Input: `approveRejectSchema` (changeOrderId, comments?)
   - Load change order — verify status is 'pco_submitted' or 'pending_approval'
   - Load approval steps ordered by stepOrder
   - Find the current pending step (first step with status='pending')
   - **Validate user can approve at this step:**
     - If step has approverUserId: ctx.userId must match
     - If step has approverRole: ctx.user.role must match (use normalized org: prefix format)
     - If neither specified: any user with ChangeOrder approve permission can approve
   - Mark step as approved (approvedBy=ctx.userId, approvedAt=now, comments)
   - Check if ALL steps are now approved:
     - **If YES (final approval):** This is a critical transaction. Within a SINGLE transaction:
       1. Generate CO number via `getNextChangeOrderNumber(db, schema.changeOrderCounters, projectId, 'co')`
       2. Update changeOrder: status='approved', coNumber=generated, approvedAt=now, approvedBy=ctx.userId
       3. **Apply budget impacts:** For each changeOrderLineItem with a budgetLineItemId:
          ```sql
          UPDATE budget_line_items SET budgeted_amount = budgeted_amount + amountChange WHERE id = budgetLineItemId
          ```
          Use `sql` template: `sql\`budgeted_amount + ${item.amountChange}\``
       4. Record history: changeType='status_change', newValue={status:'approved', coNumber}
       5. Record history: changeType='approval', newValue={step: stepOrder, approvedBy: userId}
     - **If NO (more steps pending):**
       1. If current CO status is 'pco_submitted', update to 'pending_approval'
       2. Record history: changeType='approval', newValue={step: stepOrder, approvedBy: userId, moreStepsPending: true}
   - Return updated change order with approval status

   **CRITICAL:** The budget update + status change + CO number generation MUST be in a single transaction. If any part fails, the entire operation rolls back. Use serializable isolation if Drizzle supports it, otherwise default transaction isolation is acceptable since we use SELECT FOR UPDATE on the counter row.

**9. reject** (mutation):
   - Input: `approveRejectSchema` (changeOrderId, comments?)
   - Load change order — verify status is 'pco_submitted' or 'pending_approval'
   - Load current pending approval step
   - Validate user can approve at this step (same logic as approve)
   - Mark step as rejected (status='rejected', comments)
   - Mark all remaining pending steps as 'skipped'
   - Update changeOrder: status='rejected', rejectedAt=now, rejectedBy=ctx.userId, rejectionReason=comments
   - Record history: changeType='status_change', newValue={status:'rejected', reason: comments}
   - Return updated change order
   - **Note:** After rejection, user can update the CO (edit fields/line items) and re-submit. On re-submit, new approval steps are created (old ones remain for history).

**10. void** (mutation):
   - Input: { changeOrderId: z.string().uuid(), reason: z.string().max(2000) }
   - Load change order — allow voiding from any status except already 'void'
   - If CO was 'approved': REVERSE budget impacts (subtract amountChange from budget line items) in same transaction
   - Update changeOrder: status='void'
   - Record history: changeType='status_change', newValue={status:'void', reason}
   - Return updated change order

**11. getHistory** (query):
   - Input: { changeOrderId }
   - Return all history records ordered by changedAt ASC
   - Validate user has read permission via CASL

**12. getApprovalStatus** (query):
   - Input: { changeOrderId }
   - Return all approval workflow steps ordered by stepOrder
   - For each step, include: stepOrder, approverRole, approverUserId, requirementType, status, approvedBy, approvedAt, comments
   - Include computed field: `canCurrentUserApprove` based on ctx.userId and ctx.user.role matching current pending step
