**Create `apps/api/src/calculations/payment-app.ts`:**

Implement G702 calculation functions:

```typescript
// calculateLineItemAmounts: Given a SOV item's scheduled value, previous percent complete,
// current percent complete, materials stored this period, and retainage rate:
// - workCompletedThisPeriod = ((currentPercent - previousPercent) / 100) * scheduledValue
// - totalCompletedAndStored = workCompletedThisPeriod + materialsStoredThisPeriod
// - retainageAmount = totalCompletedAndStored * (retainageRate / 100)
// Returns all calculated values as strings with 2 decimal places (for NUMERIC DB columns).

// calculatePaymentAppTotals: Given an array of calculated line items, the original contract sum,
// net change by change orders, and previous payments:
// - contractSumToDate = originalContractSum + netChangeByChangeOrders
// - totalCompletedAndStored = sum of all line items' totalCompletedAndStored
// - retainageAmount = sum of all line items' retainageAmount
// - totalEarnedLessRetainage = totalCompletedAndStored - retainageAmount
// - currentPaymentDue = totalEarnedLessRetainage - previousPayments
// - balanceToFinish = contractSumToDate - totalCompletedAndStored
// Returns all values as numbers (caller converts to strings for DB).
```

These are pure functions (no DB access). They receive pre-fetched data.

**Create `apps/api/src/trpc/routers/payment-app.ts`:**

Build the payment app router following change-order.ts patterns (protectedProcedure, loadProjectAbilities, withAuditLog, transactions):

**Procedures to implement:**

1. **create** (mutation):
   - Input: `createPaymentAppSchema`
   - Validate project exists, user has manage PaymentApp permission
   - Validate SOV items exist for project (block if no SOV)
   - For each lineItem: validate sovItemId belongs to project
   - Auto-populate previousPercentComplete for each line item:
     - Query the most recent APPROVED payment app for this project
     - For each SOV item, get the currentPercentComplete from that payment app's line items
     - If no previous payment app, previousPercentComplete = 0
   - Validate currentPercentComplete >= previousPercentComplete for each line item (can't go backwards)
   - Get retainage config from company profile (use effective-dating query pattern from Phase 2)
   - Calculate retainage rate using `getCurrentRetainageRate` based on project completion
   - For each line item: calculate amounts using `calculateLineItemAmounts`
   - Calculate totals using `calculatePaymentAppTotals`:
     - originalContractSum = sum of all SOV scheduled values
     - netChangeByChangeOrders = sum of approved change order totalAmounts for this project
     - previousPayments = sum of currentPaymentDue from all previously approved payment apps
   - Generate application number via SELECT FOR UPDATE on paymentAppCounters (reuse Phase 5 sequential-number.ts pattern, extend for payment apps)
   - Create paymentApp record with all calculated totals
   - Create paymentAppLineItems for each SOV line
   - Create retainageHeld record with total retainage for this payment app
   - Return created payment app with line items

2. **list** (query):
   - Input: { projectId, status? }
   - Return payment apps ordered by createdAt DESC
   - Include applicationNumber, periodStart/End, currentPaymentDue, status
   - Efficient: don't load line items for list view

3. **getById** (query):
   - Input: { id }
   - Return payment app with all line items (JOIN sovItems for description and scheduledValue)
   - Include approval steps and retainage held record
   - Validate project membership via CASL

4. **submit** (mutation):
   - Input: `submitPaymentAppSchema`
   - Validate status is 'draft' or 'rejected' (resubmission)
   - Create paymentAppApprovalSteps from input
   - Update status to 'submitted', set submittedAt
   - Audit log

5. **approve** (mutation):
   - Input: `approveRejectPaymentAppSchema`
   - Load payment app — verify status is 'submitted' or 'under_review'
   - Load approval steps, find current pending step
   - Validate user can approve (same pattern as change-order approve)
   - Mark step as approved
   - Check if ALL steps are now approved:
     - **If YES (final approval):** Single transaction:
       1. Update paymentApp: status='approved', approvedAt=now, approvedBy=userId
       2. **Update budget actuals (PYMT-06):** For each paymentAppLineItem:
          - Get the SOV item's budgetLineItemId
          - If budgetLineItemId exists, update the budget line item's actualCost:
            ```sql
            UPDATE budget_line_items
            SET actual_cost = actual_cost + workCompletedThisPeriod
            WHERE id = budgetLineItemId
            ```
          - Also lock the budget line item if not already locked (isLocked=true, lockedAt=now, lockedBy=userId)
       3. Audit log the approval and budget updates
     - **If NO (more steps):**
       1. Update status to 'under_review' if currently 'submitted'
       2. Audit log step approval

6. **reject** (mutation):
   - Input: `approveRejectPaymentAppSchema`
   - Validate status is 'submitted' or 'under_review'
   - Find current pending step, validate user authority
   - Mark step as rejected, skip remaining steps
   - Update paymentApp: status='rejected'
   - Audit log with rejection reason

7. **markPaid** (mutation):
   - Input: `markPaymentAppPaidSchema`
   - Validate status is 'approved'
   - Update status to 'paid', set paidAt
   - Audit log

8. **getApprovalStatus** (query):
   - Input: { paymentAppId }
   - Return all approval steps ordered by stepOrder
   - Include canCurrentUserApprove computed field

9. **getSummary** (query):
   - Input: { projectId }
   - Return aggregated summary: count by status, total approved amount, total pending amount, total paid amount
   - Useful for project dashboard card

10. **getRetainage** (query):
    - Input: { projectId }
    - Return all retainage held records for project with status
    - Include total held, total released, total eligible for release

11. **releaseRetainage** (mutation):
    - Input: { retainageId, amount, notes }
    - Validate retainage record exists and status is 'held' or 'eligible_for_release'
    - Validate amount <= amountHeld - releasedAmount
    - Update releasedAmount, releasedAt, releasedBy
    - If fully released, update status to 'released'
    - Audit log
